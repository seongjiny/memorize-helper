# 암송 기록 Supabase 연결

프런트 화면은 `src/composables/useMemorizationRecords.ts`를 통해 Supabase의 암송 기록을
조회하고 저장합니다.

## 1. 테이블과 보안 정책 생성

Supabase Dashboard의 **SQL Editor**에서 아래 SQL을 한 번 실행합니다.

```sql
create table public.memorization_records (
  id bigint generated by default as identity primary key,
  user_id uuid not null references auth.users(id) on delete cascade,
  record_date date not null,
  script_id text not null,
  book text not null,
  start_chapter integer not null check (start_chapter > 0),
  start_verse integer not null check (start_verse > 0),
  end_chapter integer not null check (end_chapter > 0),
  end_verse integer not null check (end_verse > 0),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (user_id, record_date),
  check (
    start_chapter < end_chapter
    or (start_chapter = end_chapter and start_verse <= end_verse)
  )
);

alter table public.memorization_records enable row level security;

grant select, insert, update, delete
on table public.memorization_records
to authenticated;

create policy "Users can view their own memorization records"
on public.memorization_records
for select
to authenticated
using ((select auth.uid()) = user_id);

create policy "Users can create their own memorization records"
on public.memorization_records
for insert
to authenticated
with check ((select auth.uid()) = user_id);

create policy "Users can update their own memorization records"
on public.memorization_records
for update
to authenticated
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id);

create policy "Users can delete their own memorization records"
on public.memorization_records
for delete
to authenticated
using ((select auth.uid()) = user_id);
```

`unique (user_id, record_date)` 때문에 한 사용자는 하루에 하나의 기록만 가집니다. 같은 날짜에
새 기록을 추가하면 unique 제약으로 거절됩니다. 기존 기록은 ID와 사용자 ID를 기준으로
수정합니다. 다른 자료 화면에서 기존 기록을 열어도 원래 `script_id`를 유지하며, 자료 변경은
기록 관리 화면에서 사용자가 명시적으로 선택합니다.

## 2. 생성 결과 확인

Dashboard의 **Table Editor**에서 `memorization_records` 테이블을 열고 다음을 확인합니다.

- RLS가 활성화되어 있음
- `user_id`, `record_date` 조합에 unique 제약이 있음
- SELECT, INSERT, UPDATE 정책이 각각 존재함
- DELETE 정책이 존재함

이미 이전 버전의 가이드로 테이블을 만든 경우 아래 SQL만 추가로 실행합니다.

```sql
grant delete
on table public.memorization_records
to authenticated;

create policy "Users can delete their own memorization records"
on public.memorization_records
for delete
to authenticated
using ((select auth.uid()) = user_id);
```

## 3. 프런트 연결 방식

새 기록은 `insert`, 기존 기록은 `update`를 사용합니다. 날짜 충돌 시 기존 기록을 덮어쓰지 않습니다.

```ts
await supabase.from('memorization_records').insert(record)
await supabase.from('memorization_records').update(record).eq('id', recordId).eq('user_id', userId)
```

사용자의 전체 기록을 날짜 내림차순으로 500개씩 페이지 조회합니다. 주간·월간 화면과 전체
진행률은 이 기록을 사용합니다. 한 번의 기본 응답 제한으로 오래된 기록이 누락되지 않도록
빈 페이지 또는 500개 미만의 페이지가 나올 때까지 이어서 불러옵니다.

```ts
await supabase
  .from('memorization_records')
  .select('*')
  .eq('user_id', userId)
  .order('record_date', { ascending: false })
  .range(offset, offset + 499)
```

Supabase의 API 최대 응답 행 수는 500개 이상으로 설정해야 합니다. 이 문서의 SQL은 API 행
제한 설정을 변경하지 않습니다.

계정 변경 시 프런트 기록 상태를 초기화하고 이전 요청의 응답을 무시합니다. 실제 데이터
접근 제어는 RLS 정책이 담당하며 `auth.uid()`와 `user_id`를 비교합니다. 위 SQL이 실제 프로젝트에
적용됐는지는 별도 사용자로 확인해야 합니다. 이번 변경에는 테이블 구조 변경이 없습니다.
