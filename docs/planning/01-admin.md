# 1. 어드민 페이지

상태: 기획 초안. 관련 선행 작업: [성경 DB화](01a-bible-database.md).

## 목표와 첫 범위

운영자가 코드 배포 없이 자료의 공개 상태를 관리하고, 필요한 사용자 지원 작업을 안전하게
수행할 수 있게 합니다. 사용자 관리와 구절·자료 관리는 서로 다른 작업으로 나눕니다.

| 영역 | 첫 구현 추천 | 이후 검토 |
| --- | --- | --- |
| 사용자 | 목록·최소 프로필·가입 시각·계정 상태 조회 | 정지/해제, 탈퇴 처리, 지원 목적 기록 조회 |
| 자료 | 목록·검색·초안 편집·미리보기·게시·보관 | 복수 편집자 승인, 변경 비교 고도화 |
| 구절 | 검수된 판본의 장절 조회·자료 범위 선택 | 원문 수정·대량 가져오기·번역본 추가 |
| 운영 이력 | 게시·보관 등 변경 행위와 담당자 기록 | 감사 검색·내보내기 |

원문 수정은 판본 전체에 영향을 줍니다. 자료 제목·설명·단락 구성 편집과 분리하고,
첫 단계는 검수된 원문 선택을 기본으로 추천합니다. 관리자에게 사용자 개인 암송 기록이
자동 공개되는 것으로 설계하지 않습니다. 지원 목적 조회가 필요하면 목적과 범위를 먼저 정합니다.

## 접근 방식 비교

| 방식 | 장점 | 제약 | 판단 |
| --- | --- | --- | --- |
| Supabase Dashboard로 운영 | 새 UI 없이 초기 데이터 확인·검수 가능 | 권한이 넓고 운영 실수 방지가 제품 요구와 다름 | 초기 소수 운영자의 DB 검수 도구 |
| 기존 앱의 `/admin` | 로그인·스타일 재사용, 배포 하나로 관리 | 사용자 앱과 관리자 기능의 배포가 연결됨 | 첫 어드민 추천 |
| 별도 관리자 앱·도메인 | 화면·배포·운영 역할 분리 용이 | 인증·배포 설정과 유지 비용 증가 | 운영 규모가 커지면 검토 |

관리자 화면의 주소를 숨기는 것은 접근 제어가 아닙니다. 어떤 UI를 택해도 서버의 권한
검사와 DB 정책이 필요합니다. 로그인은 기존 카카오 인증을 재사용하고 별도의 관리자 비밀번호를
첫 단계에 도입하지 않는 방향을 추천합니다.

## 사용자 흐름과 화면

1. 로그인 → 서버에서 관리자 여부 확인 → 관리자 메뉴 표시.
2. `/admin` 진입 → 자료/사용자 탭 선택.
3. 자료 검색 → 상세 → 초안 변경 → 사용자 화면 형태로 미리보기.
4. 게시 전 판본·범위·원문 출처·기존 기록 영향 확인 → 게시.
5. 공개 자료를 내릴 때는 보관 처리 → 신규 접근과 과거 기록 표시를 각각 확인.

화면 구성 제안:

```text
관리자                  [자료] [사용자] [운영 이력]
[자료 검색] [판본 필터] [공개 상태]       [자료 추가]
제목 | 판본 | 범위 | 상태 | 최근 변경 | 편집

자료 편집
제목 / 설명 / 판본 / 장절 범위 / 단락 소제목
본문 미리보기 / 검증 결과 / 변경 요약
[초안 저장] [미리보기] [게시]
```

사용자 목록은 페이지 조회와 필터를 사용합니다. 닉네임만으로 사용자를 식별하지 않고,
상세에서 안정적인 사용자 식별자와 가입 시각을 구분해 표시합니다. 정보가 없는 계정도 처리합니다.

## 권한·서버 설계

- 관리자 역할은 서버가 관리하는 역할 테이블 등으로 확인합니다. 클라이언트에서 수정할 수
  있는 프로필 필드나 사용자 메타데이터로 관리자를 판정하지 않습니다.
- 최초 관리자 지정과 해제는 제한된 운영 절차로 진행합니다. 일반 UI에 자기 승격 경로를 두지 않습니다.
- 라우터 접근 검사와 별도로, 모든 관리 API에서 로그인·역할·작업별 권한을 검증합니다.
- 공개 본문과 초안의 DB 읽기/쓰기 정책을 분리합니다. 일반 사용자는 초안을 읽거나 게시할 수 없습니다.
- Auth 사용자 목록/계정 처리가 필요한 API는 Supabase Edge Function 같은 서버 경계에서 실행합니다.
  서비스 권한 키를 브라우저·`VITE_*`·저장소에 넣지 않습니다.
- 사용자 목록 API는 필요한 필드만 반환하며 페이지 수·검색 범위를 제한합니다.
- 운영 이력은 서버에서 남기고 일반 사용자가 생성·수정·삭제할 수 없게 합니다.
  자료 게시와 이력 저장은 하나의 트랜잭션으로 처리합니다.
- 최초 범위에 포함하지 않은 정지·삭제 API는 UI와 함께 별도 설계합니다.
  계정 정지만 해도 이미 발급된 세션이나 개인 테이블 접근이 즉시 차단되는지 따로 검증해야 합니다.

최소 데이터 제안: `admin_roles`, `admin_audit_logs`, 공개 자료·초안 테이블.
사용자 목록은 Auth 관리 API를 사용하고, 별도 `profiles` 테이블은 제품에 필요한 필드가 있을 때
추가합니다. 관리자 전체가 모든 원문·계정 삭제 권한을 가지는 구조는 첫 단계부터 피합니다.

## 하위 작업

- [ ] 관리 목적과 사용자 조회 필드·권한표 확정.
- [ ] 자료 관리용 구조화 데이터와 게시/보관 정책 준비.
- [ ] 관리자 부여·해제 절차, API 권한 검사, DB 정책 작성.
- [ ] 조회 전용 관리 화면 구현 후 권한 테스트.
- [ ] 자료 초안 편집·장절 검증·미리보기 구현.
- [ ] 게시·보관·충돌 감지와 서버 감사 이력 구현.
- [ ] 사용자 목록 조회 구현. 정지·삭제는 별도 범위 확정 후 진행.

## 테스트할 것

| 경우 | 기대 결과 |
| --- | --- |
| 익명·일반 사용자가 `/admin` 직접 접근 | 관리 데이터와 작업 화면 접근 거절 |
| 일반 사용자가 API·DB 요청을 직접 조작 | 서버/DB에서도 거절; UI 검사 우회 불가 |
| 프로필에서 관리자라고 주장 | 권한 변화 없음 |
| 관리자 해제 또는 세션 만료 | 다음 관리 요청 거절, 민감 화면 상태 초기화 |
| 자료 초안 저장·게시·보관 | 일반 사용자에게는 게시된 허용 자료만 공개 |
| 관리자 두 명이 같은 초안을 변경 | 버전 비교로 덮어쓰기 충돌 안내 |
| 존재하지 않는 절·역순 범위·빈 제목 | 게시 거절, 수정 위치 안내 |
| 게시 중 실패 | 자료와 감사 이력이 부분 완료 상태로 남지 않음 |
| 사용자 조회 응답 | 불필요한 인증 정보·비밀값 미반환 |
| 보관한 자료를 참조하는 기존 기록 | 기존 기록 표시·범위·사용자 연결 유지 |

브라우저 모킹 테스트와 실제 테스트 DB의 권한 검증을 모두 수행합니다.

## 완료 기준과 결정할 사항

최초 관리자가 지정되고 일반 사용자의 직접 요청이 거절되며, 초안→미리보기→게시→보관을
수행해도 기존 기록이 보존되면 자료 관리 첫 단계가 완료됩니다. 사용자 목록은 별도 완료 단위입니다.

결정할 사항:

1. 우선순위: 자료 운영부터 / 사용자 조회부터. 추천은 자료 운영부터.
2. 사용자 관리 범위: 조회만 / 정지까지 / 탈퇴 삭제까지. 추천은 조회만.
3. 구절 관리 의미: 검수 원문으로 자료 구성 / 원문 자체 수정. 추천은 자료 구성부터.
4. 관리자 수와 역할: 운영자 한 명 / 여러 편집자. 여러 명이면 충돌 관리가 특히 필요합니다.
