테스트, 완료 기준, 결정할 사항을 포함합니다.

## 현재 구현에서 확인한 사실

- Vue 3·TypeScript·Vite와 Supabase Auth를 사용합니다.
- 본문은 JSON 자료 3개이고, 목록은 `src/data/database.ts`에 있습니다.
- 장절은 문자열에서 추출합니다. 전체 성경을 검증하는 표준 장절 DB는 없습니다.
- 로그인 없이 본문을 읽고 가리기/열기 연습을 할 수 있습니다.
- 암송 기록은 사용자별 하루 하나입니다. 과거 날짜 입력·수정·삭제가 가능합니다.
- 자료별 진행률은 저장 범위가 덮는 고유 절 비율입니다. 실력이나 시험 점수가 아닙니다.
- `/records`에 주간 목록과 월간 달력이 이미 있습니다.
- 관리자 권한·관리자 API·읽기 모드 전환·시험·배지는 구현되어 있지 않습니다.
- 운영 DB에 문서의 SQL이 적용됐는지는 이번 기획에서 확인하지 않았습니다.

## 먼저 합의할 공통 기준

| 질문 | 추천 초안 | 바뀌면 영향을 받는 기능 |
| --- | --- | --- |
| 하루 기록 수 | 첫 단계는 현재의 하루 한 기록 유지 | 달력·성취·시험 결과 연동 |
| 활동한 날의 의미 | 저장된 암송 기록이 있는 날짜 | 달력·성취 |
| 읽기만 한 날 | 암송 활동 날짜에 자동 포함하지 않음 | 읽기·달력 |
| 시험 완료 | 기존 암송 기록을 자동 생성·덮어쓰지 않음 | 시험·달력·성취 |
| 날짜 기준 | 첫 단계는 기기 로컬 날짜 유지 | 달력·성취·기록 |
| 주 시작 | 기존 화면과 같은 일요일 | 달력·기록 |
| 진행률 | 자료별 고유 절 범위 비율 유지 | 자료 카드·달력·성취 |
| 과거 기록 | 달력과 기록 기반 성취에 포함 | 달력·성취 |

같은 본문을 반복한 날도 활동 날짜로는 1일입니다. 자료별 진행률은 같은 절을 중복 계산하지
않습니다. 화면에는 ‘기록한 날’, ‘기록 범위 진행률’처럼 측정한 대상을 명시합니다.

여러 자료·읽기·시험을 하루 활동에 함께 반영하려면 날짜별 기록과 별도로 활동 이벤트 모델이
필요합니다. 그 확장은 이번 첫 단계에 섞지 않고 별도 데이터 변경으로 다룹니다.

## 선행 관계와 추천 진행 순서

| 순서 | 작업 | 이유·선행 조건 |
| --- | --- | --- |
| 0 | 모드 의미·활동 기준·관리자 범위 결정 | 서로 다른 기능이 같은 기록을 다르게 해석하는 문제 방지 |
| 1 | 읽기 모드 | 정적 JSON으로 가능하고 기존 암송 기능과 분리하기 쉬움 |
| 2 | 메인 달력 | 현재 기록과 월간 달력을 활용해 바로 효용을 확인 |
| 3 | 기록 기반 성취 | 달력과 공유할 날짜·연속 기록 계산이 먼저 정리됨 |
| 4 | 음성 시험 기술 검증 → 시험 화면 | 기존 자료로 녹음·인식·70점 기준 검증; 자기 확인은 대안 |
| 별도 기반 작업 | 본문 출처·이용 조건 확인 → 구조화 → 성경 DB 이전 | 구절 관리 어드민과 채점 확장의 기반 |
| 기반 작업 이후 | 관리자 권한·API → 자료 관리 → 사용자 관리 | UI보다 서버 권한과 데이터 보존을 먼저 검증 |

어드민이 가장 급하면 기반 작업과 관리자 작업을 먼저 진행할 수 있습니다. 사용자 목록만
관리하는 어드민은 성경 DB에 의존하지 않습니다. 구절·자료 편집 어드민은 의존합니다.
전체 성경을 먼저 수집할 필요는 없고, 현재 자료부터 정확히 이전하는 접근을 추천합니다.

## 구현 전 공통 검토와 테스트

- 기능별 화면·빈 상태·실패 상태·권한별 동작을 검토합니다.
- 날짜 계산은 자정·월말·윤년·시간대 변경 예제로 검증합니다.
- 새 DB 정책은 실제 Supabase 테스트 환경에서 익명·사용자 A/B·관리자로 검증합니다.
- 계정 변경 시 이전 계정 데이터와 늦게 도착한 응답이 표시되지 않아야 합니다.
- 기존 10개 브라우저 테스트를 회귀 기준으로 유지합니다. 새 기능별 테스트는 각 문서에 있습니다.
- 코드가 변경되는 구현 단계에는 타입 검사·빌드·ESLint와 해당 기능 테스트를 실행합니다.
- 본문 문장 정확성과 이용 조건은 별도 검수가 필요합니다. 기존 테스트는 이를 보증하지 않습니다.

## 작업 단위

이번 작업 브랜치는 `feature/next-feature-planning`이며 문서만 작성합니다.
구현은 기능별 브랜치와 작은 변경으로 나눠 `dev`에서 검증하는 흐름을 제안합니다.
운영 데이터 변경은 테스트 DB에서 이전·복구 절차까지 확인한 뒤 별도로 진행합니다.

시험은 음성 인식과 점수·합격선 조절 방향으로 보완했습니다. 다음 검토에서는 채점 단위·전체 합격 조건,
읽기 의미, 어드민 첫 범위, 배지 기준, 달력 표현부터 선택하면 됩니다.
각 문서 마지막에 선택지를 모았습니다. 일정은 이 선택과 데이터 이용 조건 확인 후 산정합니다.
